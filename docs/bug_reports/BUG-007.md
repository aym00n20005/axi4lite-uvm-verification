## Expected

Verification plan §4: the cover property `c_w_before_aw` *"exists to prove this
is actually happening"* — that the driver runs genuinely independent
per-channel threads. The README is blunter: *"if it stays uncovered, none of
your protocol testing is real."*

The cover point is therefore load-bearing. It is the evidence for a claim made
about the whole environment.

## Actual

```systemverilog
c_aw_before_w : cover property (aw_acc ##[1:$] w_acc);
c_w_before_aw : cover property (w_acc  ##[1:$] aw_acc);
```

`##[1:$]` is unbounded and the terms are unqualified, so a match may **start in
one transaction and complete in another**. Any W accept followed eventually by
any AW accept satisfies `c_w_before_aw` — including the W of transaction 3 and
the AW of transaction 7.

Both cover points are therefore hit by any multi-transaction run, whatever the
ordering inside each transaction.

## Why this is worse than an uncovered cover point

The failure mode is inverted from the one the README warns about. The risk was
never that `c_w_before_aw` would stay uncovered — it is that it **cannot** stay
uncovered, so it can never warn about anything.

A driver that lockstepped AW and W, never producing W-before-AW in a single
transaction, would still show this cover point green. The environment would
report that it had proven something it had not tested.

## Evidence

Same testbench, same stimulus, nothing changed but the property text:

| Cover point | Unqualified | Qualified |
|---|---|---|
| `c_aw_before_w` | 10 | **1** |
| `c_w_before_aw` | 10 | **1** |

`sanity_tb` contains exactly one genuine occurrence of each ordering. The
unqualified form reported ten, of which nine were cross-transaction artefacts.

## Root cause

The property was written to describe the *sequence of bus events* rather than
the *state of a transaction*. AXI4-Lite has no transaction ID in this design,
so bus events alone cannot delimit a transaction — the pending-flags are the
only thing that can.

## Fix

Qualify both ends on the checker's own pending-flags:

```systemverilog
c_aw_before_w : cover property ((aw_acc && !w_pend)  ##[1:$] (w_acc  && aw_pend && !b_done));
c_w_before_aw : cover property ((w_acc  && !aw_pend) ##[1:$] (aw_acc && w_pend  && !b_done));
```

`w_pend` can only still be set at the AW accept if no B response has
intervened, and a B response cannot occur without `aw_pend`. That confines the
match to a single transaction. The `!b_done` term excludes the one remaining
escape: a back-to-back accept landing on the cycle the previous response
completes, where the flag has not yet cleared.

## Regression

Counts fell from 10 to 1 on each, with all 31 `sanity_tb` checks still passing
and no assertion firing. Both orderings remain covered, so the fix tightened
the property without losing the stimulus it was meant to detect.

## What it changes about the project

The checker had been treated as trustworthy because it was carefully written
and its assertions fire correctly — BUG-002 confirms that. This defect was in
the **cover** properties, which are the part nobody watches fail, because they
have no failure mode. They are either hit or not, and a hit is assumed to mean
what it says.

Cover points that assert something about the environment need the same scrutiny
as assertions about the DUT. Reviewing a cover count for plausibility — *should
this really be 10 when the bench contains one such case?* — is what found it.
