# BUG-009 — Driver channel threads not aligned to the clocking grid

*Genuine defect, found in the UVM driver when a second DUT shifted the timing.*

| Field | Content |
|---|---|
| **ID** | BUG-009 |
| **Class** | **Genuine find** — a race that had been passing for eleven days |
| **Located in** | `axi_driver`, all five channel tasks |
| **Detected by** | `axi_mem_test` hanging; diagnosed by the watchdog and a cycle trace |
| **Date** | 27 August 2026 |
| **Status** | Fixed. |

---

## Symptom

`axi_mem_test` hung on its first transaction. EDA Playground killed the run with
exit 137 and no message.

The watchdog — added in response, because a hang was the one failure this
environment could not report — produced a state that looked impossible:

```
AW  VALID=0 READY=1  ADDR=0x00001000
W   VALID=0 READY=1  DATA=0xcafebabe STRB=1111
B   VALID=0 READY=1  RESP=00
```

The payload was driven, so the channel threads had run. `BREADY` was high, so
`b_channel` had its transaction and was waiting. Yet every VALID was low and the
bus was idle. A cycle trace confirmed it over 40 clocks: `AWVALID` never rose,
`aw_captured` never set.

Payload driven but VALID low is impossible from a single statement sequence.
That contradiction is what said the fault was in my model of the code rather
than in the hardware.

## Root cause

```systemverilog
aw_q.get(t);                                   // resumes at an arbitrary time
repeat (t.aw_delay) @(vif.master_cb);          // aw_delay == 0: no wait at all
vif.master_cb.AWADDR  <= t.addr;
vif.master_cb.AWVALID <= 1'b1;
do @(vif.master_cb); while (vif.master_cb.AWREADY !== 1'b1);
vif.master_cb.AWVALID <= 1'b0;
```

A clocking-block output assignment takes effect at the **next clocking event
plus the output skew**. `aw_channel` resumes when `dispatch()` puts to its
mailbox — at whatever moment the sequencer handshake happens, which is not
necessarily a clocking event — and with `aw_delay == 0` nothing re-aligns it.

The assert and the deassert can then resolve to the **same** clocking event, and
the later write wins:

```
AWVALID <= 1'b1;                  -> event E
do @(cb); while (!AWREADY);       -> returns at E
AWVALID <= 1'b0;                  -> also E, and wins
```

`AWADDR` is written once, so it survives. `AWVALID` is written twice, so it
never rises. That is precisely the observed state.

## Why it passed for eleven days

The register-slave tests — `axi_smoke_test` and `axi_random_test`, 44 checks and
166 random transactions — all passed. Whether the race bites depends on when
dispatch happens to land relative to the clock, and on the register slave it
always landed safely. A different DUT, a different sequence, a different phase
of the run, and the luck ran out.

**The non-UVM benches never had the bug.** Every task in `sanity_tb.sv` begins
`@(posedge ACLK)`. The UVM driver was written from the design notes rather than
from the working bench, and the alignment was dropped without anyone noticing it
was load-bearing.

## Fix

Every channel task now aligns to the clock grid before driving:

```systemverilog
aw_q.get(t);
@(vif.master_cb);                  // align to the clock grid
repeat (t.aw_delay) @(vif.master_cb);
```

Applied to all five — AW, W, B, AR and R. The B and R paths had the same
exposure whenever their ready-delay randomised to zero.

## Regression

`axi_mem_test` 17/17, 0 errors, 25 responses checked, 0 mismatches, three-way
count 12/13. Local non-UVM regression unchanged at 31/31 and 27/27.

The cycle trace after the fix:

```
55000 | AWv=1 AWr=1 | Wv=1 Wr=1 | Bv=0 |  <- both halves accepted, same cycle
65000 | AWv=0 AWr=0 | Wv=0 Wr=0 | Bv=1 |  <- BVALID exactly one cycle later
```

## What it changes about the environment

**A hang was undiagnosable.** Assertions fire, the scoreboard mismatches, the
three-way count catches drops — but a stalled handshake produced an exit code
and silence. The watchdog is now permanent in both tops, and it turned an
unreadable timeout into a diagnosis in one run.

**A passing test is not evidence that the driver is correct**, only that this
particular timing did not expose it. The bug was latent through every test the
project had, including 166 random transactions, because randomising the
*payload* does not randomise *when the sequencer handshake lands relative to the
clock*.
