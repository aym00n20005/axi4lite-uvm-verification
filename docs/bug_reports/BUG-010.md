# BUG-010 — Two constraints written in a form the LRM grammar does not allow

*Genuine defect, found in the testbench. Not injected.*

| Field | Content |
|---|---|
| **ID** | BUG-010 |
| **Class** | Genuine find — fourth, and the fourth to be in the testbench rather than the design |
| **Located in** | `tb/agent/axi_transaction.sv`, `c_strb_dist` and `c_strb_reg` |
| **Detected by** | **slang elaboration** — the first thing a conformant front end was ever pointed at this code |
| **Test + seed** | None. No simulation was involved; the defect is in what the source *means*, and every simulation of it had been run by the one tool that accepts the form. |
| **Status** | Fixed. Both constraints re-expressed; distribution unchanged. |

## Expected

Two of `axi_transaction`'s constraints steer the write-strobe distribution, and
both are meant to be **soft** so that a sequence can override them with
`with { strb == 4'b1111; }` and get a directed transaction instead of a
contradiction. The file says so:

> *SOFT, so a sequence can write `with { region == REGION_MEM; }` and steer the
> traffic without producing a constraint contradiction. Every distribution
> constraint below is soft for the same reason.*

## Actual

```systemverilog
constraint c_strb_dist {
    soft (kind == AXI_WRITE) -> strb dist { ... };
}
```

IEEE 1800-2017 §18.5 gives `constraint_expression` several alternatives. Two of
them matter here:

```
constraint_expression ::= [ soft ] expression_or_dist ;
                        | expression -> constraint_set
```

`soft` attaches to the **first** production only. Writing `soft` in front
therefore commits the parser to that alternative, and the `->` that follows is
no longer the constraint-implication operator — it is the ordinary boolean
implication **operator**, inside a single expression. Its right-hand operand is
`strb dist { ... }`, and `dist` is not an expression. The line is ill-typed:

```
error: invalid operands to binary expression ('bit' and 'void')
    soft (kind == AXI_WRITE) -> strb dist {
          ~~~~~~~~~~~~~~~~~  ^~ ~~~~~~~~~~~
```

Two constraints, `c_strb_dist` and `c_strb_reg`, were written this way. The
other four soft constraints in the file — `c_region_dist`, `c_align_dist`,
`c_delay_dist`, `c_kind_dist` — are plain `soft <var> dist {...}` with no
implication, which is the legal first production, and are unaffected.

## Why it survived

Xcelium accepts it. Every measured result this project has published for
`axi_random_test` — 166 transactions, the 48.8%-error measurement that led to
the current weights, the coverage tallies — came from a simulator that parsed
this form without complaint. Nothing in the output distinguished it from
correct source.

That is the whole reason it took a **different tool** to find it, rather than
another test. No amount of stimulus interrogates the meaning of a constraint
the parser has already resolved; only a second parser does.

## Root cause

Precedence, and an easy assumption: that `soft` is a modifier on the *whole*
constraint expression, like a qualifier. It is not — it is part of one specific
production, and putting it in front silently changes which production the
parser selects.

## Fix

Move `soft` inside the implication, onto the `dist` it was always meant to
qualify:

```systemverilog
constraint c_strb_dist {
    (kind == AXI_WRITE) -> soft strb dist { ... };
}
```

Now `expression -> constraint_set` is selected, the `constraint_set` is a
`constraint_expression`, and `[ soft ] expression_or_dist` applies to the dist —
which is what the comment always said the code did. The distribution weights are
untouched.

## Regression

- slang: 2 errors → **0 errors** across all five bundles.
- `sanity_tb` 31/31 and `sanity_mem_tb` 27/27 still pass — neither bench
  instantiates `axi_transaction`, so this confirms no collateral damage rather
  than confirming the fix.
- The fix is verified by elaboration, not by simulation, and that is the
  honest statement of it. Whether Xcelium's randomisation changes is a separate
  question, answered by the next Playground run: if the weights it produced were
  already the intended ones, nothing moves.

## What it changes about the project

`docs/tooling_notes.md` has always argued that tool capability is measured
rather than assumed, and it has three entries in that spirit: Icarus cannot do
concurrent assertions, Riviera compiles UVM but is not licensed to simulate it,
Verilator's `--coverage` crashes where `--coverage-user` does not. This adds a
fourth of a different kind — not *what a tool cannot do*, but **what a tool
accepts that it should not**.

The other three cost time. This one cost correctness, quietly, for three weeks,
and no test could have found it. A single conformant front end run over the
existing sources found it in 0.2 seconds, which is a strong argument for having
one in the flow at all — see `scripts/elab.sh`.

The lesson generalises past this bug: **a testbench validated by exactly one
simulator is validated against that simulator's extensions as much as against
the language.** Everything this project has ever run, it ran on Xcelium alone.
