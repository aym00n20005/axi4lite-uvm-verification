# BUG-003 — Memory slave ignores WSTRB

*Injected for qualification. Spec §9.*

| Field | Content |
|---|---|
| **ID** | BUG-003 |
| **Class** | Injected — not a genuine defect |
| **Detected by** | **Scoreboard**, as §9 requires |
| **Test + seed** | `axi_mem_test`, directed, Xcelium `SVSEED default: 1` |
| **Date** | 27 August 2026 |
| **Status** | Detected, reverted. `main` has never carried it. |

---

## Injection

One condition deleted from the byte-lane loop in `axi4lite_mem_slave`:

```systemverilog
-  if (wr_strb[b]) mem[wr_word][8*b +: 8] <= wr_data[8*b +: 8];
+  mem[wr_word][8*b +: 8] <= wr_data[8*b +: 8];
```

Every write now updates all four bytes regardless of `WSTRB`.

## Expected

Spec §6: byte *n* is written only when `WSTRB[n]` is 1, and `WSTRB == 4'b0000`
is a legal no-op returning `OKAY` with memory unchanged.

## Detected by the scoreboard

```
[SB] 12 writes, 13 reads | 25 responses checked
     | 13 read-data checked, 0 skipped | 6 mismatches
```

Six RDATA mismatches against the byte-lane reference model, and six of the
sequence's seventeen checks failed. The most damaging:

```
[SB] RDATA mismatch ... got 0xffffffff expected 0x11bb33dd
FAIL  memory unchanged   0xffffffff (expected 0x11bb33dd)
```

A legal zero-strobe no-op became a full-word overwrite. Responses stayed `OKAY`
throughout — the bug is invisible on the response channel, which is why an
assertion could not catch it and why §9 assigns it to the scoreboard.

## Why this took until 27 August

§9 has required scoreboard detection since the plan was written. `sanity_mem_tb`
caught the same injection on 17 August with six failures, but a directed bench
comparing against hardcoded expectations is not a scoreboard, and the earlier
claim in this project that the scoreboard would discharge it was wrong: the
scoreboard modelled the register slave, and `tb_top` had no memory DUT.

It was reachable only once the memory slave entered the UVM environment with
`tb_top_mem` and the scoreboard gained an associative-array memory model with
per-byte validity tracking.

## One check passed under the bug, and that is the lesson

```
PASS  WSTRB=1000 -> byte 3 only    0xaabbccdd
```

Memory held `0x00BBCCDD`. The write was `0xAABBCCDD` with strobe `4'b1000`.
Correct behaviour writes byte 3 only, giving `0xAABBCCDD`. The bug writes all
four bytes, giving `0xAABBCCDD`. **Identical**, because the write data already
matched what was in bytes 0–2.

A single-lane check can pass under this bug by coincidence of data. What
discriminates is the *cumulative* sweep — where earlier lanes leave contents
that differ from the next write — and the non-contiguous and zero-strobe cases.
Stimulus that looks thorough bin by bin can still be blind if the data does not
differ where the bug does.

## Fix

Restore the `if (wr_strb[b])` guard. `main` has never carried the injection: it
was applied, the design pane generated, and the RTL reverted in the same step.

## Regression

After reverting: `axi_mem_test` 17/17, 0 mismatches. Local non-UVM regression
31/31 and 27/27.

## Known cosmetic issue in the failure message

The scoreboard's mismatch line reads:

```
RDATA mismatch on READ  REGION_REG_IMPL  addr=0x00001014
```

`0x00001014` is in the memory region, not `REGION_REG_IMPL`. The monitor does
not set `region` on a reconstructed transaction, so `convert2string()` prints
the enum's default. Harmless to the check — the address and the data are both
correct — but a failure message is what gets read at 2am, and this one is
misleading. Not fixed here: the run above is the verified qualification result
and it should not be re-recorded against changed code.
