# BUG-014 — A transaction reset took away, that nothing ever retired

*Genuine defect, found in the testbench. Not injected.*

| Field | Content |
|---|---|
| **ID** | BUG-014 |
| **Class** | Genuine find — eighth, and the eighth in the testbench |
| **Located in** | `tb/agent/axi_driver.sv`, `on_reset` |
| **Detected by** | `axi_reset_seq`'s mid-write case, on Xcelium |
| **Test + seed** | `axi_protocol_test`, seed 1 — **watchdog, simulation killed at 40 µs** |
| **Status** | Fixed, and the fix is **verified by re-run**: `axi_protocol_test` completes in 23.6 µs with 235 checks, 0 failures, and `cg_reset` closed at 3/3 for the first time. |

---

## Expected

Reset abandons any transaction in flight. Every abandoned transaction gets
`completed = 1` so that a sequence blocked on `wait (t.completed)` is released,
and `aborted = 1` so it can tell what happened. That is what
[the reset handling](../../tb/agent/axi_driver.sv) was written to do, and it is
what the end-of-test count check depends on.

## Actual

```
UVM_INFO @ 1255000: [axi_driver] ARESETn fell -- abandoning in-flight transactions
UVM_INFO @ 1305000: [axi_driver] reset released; starting channel threads
UVM_INFO @ 1305000: [axi_monitor] RESET low 5 cycles during a WRITE
UVM_INFO @ 1305000: [axi_scoreboard] reset: register model returned to its
                    spec section 5 values; memory untouched (section 6)

=================== WATCHDOG ===================
 no bus activity for 20000 ns. ARESETn=1
   AW  VALID=0 READY=1   W VALID=0 READY=1   B VALID=0 READY=0
================================================
```

Everything about the reset itself worked — the driver announced it, the monitor
classified it as `during a WRITE`, the scoreboard reset its model
([BUG-011](BUG-011.md)'s fix, doing its job). Then the simulation sat completely
idle for 20 µs and the watchdog killed it.

The sequence was blocked on `wait (t.completed == 1'b1)` for a transaction that
nothing would ever complete.

## Root cause

`on_reset` drained the five channel mailboxes and retired everything it found:

```systemverilog
while (b_q.num() != 0) begin
    void'(b_q.try_get(t));
    t.aborted = 1'b1; t.completed = 1'b1;
end
```

But `b_channel`'s **first act** is `b_q.get(t)`. Once it has done that, the
transaction is *no longer in the mailbox* — it is a local variable inside a
thread that `disable fork` is about to destroy. Draining the queues finds
nothing, the handle dies with the thread, and the only object that could have set
`completed` is gone.

The mailboxes hold what has **not been started**. Nothing held what was **in
progress**.

## Why it did not show up before

The mid-write case is the *only* stimulus in the project that resets a
transaction after a channel has dequeued it. The earlier run of this same
sequence never got there: `aw_delay == 25` violated a hard constraint, the
`randomize()` failed, and the transaction completed before reset arrived. Fixing
that constraint is what let the test finally do the thing it was written to do —
and it immediately found this.

**A test that fails for the wrong reason hides what it was written to check**,
and it hid this for one run.

## Fix

Track the in-flight transaction outside the mailboxes. Spec §1 caps outstanding
transactions at one read and one write, so one handle each suffices *by
construction*:

```systemverilog
axi_transaction cur_write, cur_read;   // set in dispatch, cleared on completion

// on_reset, after draining the queues:
if (cur_write != null && !cur_write.completed) begin
    cur_write.aborted = 1'b1; cur_write.completed = 1'b1;
    aborted_writes++;
end
```

## What it says about the environment

The watchdog earned itself here, and specifically the **inactivity** watchdog
rather than the absolute one it replaced. This failure is a bus that has gone
permanently quiet with every VALID low and every READY high — no assertion fires,
no scoreboard mismatch, no check fails. Under an absolute deadline it would have
looked like a slow test; under EDA Playground's own job kill it would have been
exit 137 and no message at all.

Instead the log names the state of all five channels at the moment nothing was
happening, which is what made the diagnosis a minute's work rather than an
afternoon's.

It also belongs to the same family as [BUG-009](BUG-009.md): both are about a
handle held in a place nobody thought to look, and both were invisible until a
test happened to create the timing that exposed it.
