# BUG-008 — Alignment assertion times out on a correct DUT

*Genuine defect, found in the protocol checker by constrained-random traffic.*

| Field | Content |
|---|---|
| **ID** | BUG-008 |
| **Class** | **Genuine find** — false positive, not a missed detection |
| **Located in** | `axi4lite_protocol_checker.a_misaligned_write_errors` |
| **Detected by** | `axi_random_test`, first run |
| **Test + seed** | `axi_random_test`, Xcelium `SVSEED default: 1` |
| **Date** | 23 August 2026 |
| **Status** | Fixed. |

---

## Symptom

Two failures in a 166-transaction run:

```
*E,ASRTST (./design.sv,269): (time 10005 NS) Assertion
tb_top.dut.u_chk.g_align.a_misaligned_write_errors has failed
Misaligned write did not return an error response
```

Meanwhile the scoreboard, checking the same 166 transactions against a
spec-derived reference model, reported **0 mismatches**. Two independent
checkers disagreeing about the same traffic.

## Which one was right

The scoreboard. The DUT was correct; the assertion was wrong.

```systemverilog
a_misaligned_write_errors : assert property
    ((aw_acc && (AWADDR[1:0] != 2'b00)) |-> ##[1:8] (BVALID && BRESP != 2'b00));
```

The property starts a timer at the **AW accept** and requires a response within
eight cycles. But `BVALID` cannot assert until **W has also been accepted** —
spec §3 rule 5, which `a_bvalid_not_early` enforces in the same file. The
interval between AW and W is chosen by the **master** and is bounded by nothing
in the specification.

`axi_transaction.w_delay` randomises to 20. Any AW-first write with
`w_delay > 8` misses the window and fails a completely correct slave.

## Root cause

The property conflates *"the address was accepted"* with *"the transaction is
under way"*. Only the second implies a response is due, and reaching it needs
an event the slave does not control.

The same file gets this right two assertions earlier:

```systemverilog
a_b_not_stalled : assert property ((aw_pend && w_pend) |-> ##[0:8] BVALID);
```

That antecedent requires **both** halves, so the master-controlled delay is
already spent before the timer starts. The alignment check was written with an
`aw_acc` antecedent and inherited a timing assumption that does not hold.

`a_misaligned_read_errors` has the identical structure and could not fail: a
read has no second channel to wait for, so `RVALID` always follows the AR
accept by exactly one cycle. It was fixed anyway — it was correct by accident,
not by construction.

## Fix

Check at the **response**, with no timing window at all. The checker now latches
the accepted addresses:

```systemverilog
logic [ADDR_WIDTH-1:0] aw_addr_q, ar_addr_q;
always_ff @(posedge ACLK) begin
    if (aw_acc) aw_addr_q <= AWADDR;
    if (ar_acc) ar_addr_q <= ARADDR;
end

a_misaligned_write_errors : assert property
    (BVALID |-> (aw_addr_q[1:0] == 2'b00) || (BRESP != 2'b00));
```

Read as: *at every response, either the address was aligned or the response is
an error.* Single-outstanding (spec §1) guarantees `aw_addr_q` belongs to the
write being answered.

This is stronger as well as correct — the old form permitted any error response
inside the window, the new form constrains every response.

## Why it took random traffic

Every directed test used `aw_delay` and `w_delay` of **4 or less**, comfortably
inside the eight-cycle window. The bug was unreachable by the entire directed
suite — 44 checks across the smoke test, plus 58 in the non-UVM benches — and
appeared twice within the first 150 random transactions.

The constraint that found it was written on 19 August and measured over 500
items by `axi_rand_smoke`, but had never driven a pin until 23 August. It found
this on its first contact with the DUT.

## Why a false positive is the bad kind

A missed detection leaves a bug in the design. A **false** detection is worse
for the testbench: a checker that fails on correct hardware gets muted or
ignored, and is then worthless on the day it is right.

It also cost nothing to believe. The scoreboard said the DUT was fine, the
assertion said it was not, and only reasoning from spec §3 rule 5 separates
them. Had the environment contained only the assertion, the obvious next step
would have been to "fix" a correct DUT.
