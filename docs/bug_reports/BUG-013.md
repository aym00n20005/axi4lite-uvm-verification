# BUG-013 — An inline constraint that randomised the field it pinned

*Genuine defect, found in the testbench. Not injected.*

| Field | Content |
|---|---|
| **ID** | BUG-013 |
| **Class** | Genuine find — seventh, and the seventh in the testbench |
| **Located in** | `tb/ral/axi_reg_adapter.sv`, `reg2bus` |
| **Detected by** | `axi_ral_test`, on the first run that reached the RAL at all |
| **Test + seed** | `axi_ral_test`, seed 1 — **644 `UVM_ERROR`** |
| **Status** | Fixed. Verified twice — by a standalone experiment (below) and by a clean re-run: `axi_ral_test` now reports **0 `UVM_ERROR`**, 18/18 checks, and `hw_reset` and `bit_bash` both complete silently. |

---

## Expected

`reg2bus` turns a `uvm_reg_bus_op` into an `axi_transaction`. The address, data
and kind come from the RAL and must be used exactly; only the timing knobs are
free to randomise.

## Actual

```
UVM_ERROR [RegModel] Register "regmodel.CTRL" value read from DUT (0x00000000000000ff)
                     does not match mirrored value (0x0000000000000000)
UVM_ERROR [RegModel] Register "regmodel.ID"   value read from DUT (0x0000000000000000)
                     does not match mirrored value (0x00000000deadbeef)
UVM_ERROR [uvm_reg_bit_bash_seq] Writing a 1 in bit #0 of register "regmodel.CTRL"
          with initial value 'h0 yielded 'h0000000098446fb0 instead of 'h1
```

`0x98446fb0`, `0x895b7efd`, `0x13e3d9a7` — those are not register values, they are
*random numbers*. `CTRL` read back `0xff`, which is `CONFIG`'s reset value.
`Status was UVM_NOT_OK` appears hundreds of times.

Every RAL access was going to a **random address** carrying **random data**.

## Root cause

```systemverilog
if (!t.randomize() with {
        kind == local::t.kind;
        addr == local::t.addr;      // <-- tautology
        data == local::t.data;
        strb == local::t.strb;
    })
```

IEEE 1800-2017 §18.7.1: `local::` resolves an identifier **in the scope of the
calling method, rather than in the scope of the object being randomised.**

In `reg2bus` the calling scope's `t` *is* the object being randomised. So
`local::t.addr` dereferences that handle to `t.addr` — the `rand` variable itself
— and the constraint reduces to `addr == addr`. Always true. The solver was left
completely free.

**The idiom is right; applying it to the object itself is not.**
`axi_base_seq::write()` uses it correctly:

```systemverilog
task write(input bit [31:0] addr, ...);
    ...
    t.randomize() with { addr == local::addr; }   // correct
```

There the calling scope's `addr` is a **task argument** — a different object from
the transaction's field — and `local::` is exactly what disambiguates them. In
the adapter there was no name collision to resolve, so reaching for `local::` did
not disambiguate anything; it just pointed the constraint back at itself.

## Verified, not assumed

The claim "this constraint is a tautology" is strong enough to be worth checking
directly rather than inferring from a failure. A standalone experiment, 200
iterations of each form:

```
  form A  local::a.addr : 200 of 200 randomized away from the wanted value
  form B  plain local   :   0 of 200 randomized away from the wanted value
```

## Fix

Plain locals, with names deliberately **different** from the transaction's
fields, so there is no collision and no temptation to reach for `local::`:

```systemverilog
axi_kind_e ral_kind = (rw.kind == UVM_WRITE) ? AXI_WRITE : AXI_READ;
bit [31:0] ral_addr = rw.addr;
bit [31:0] ral_data = rw.data;

t.randomize() with {
    kind == ral_kind;
    addr == ral_addr;
    data == ral_data;
    strb == 4'b1111;
    misaligned == 1'b0;
};
```

## The re-run

```
[axi_ral_seq] axi_ral_seq: 18 checks, 0 failures
[SB] 482 writes, 488 reads | 970 responses checked
     | 488 read-data checked, 0 skipped as unpredictable | 0 mismatches
UVM_ERROR :    0
```

Two numbers in there are the fix, not just its absence of errors:

- **`0 skipped as unpredictable`**, where the broken run skipped **133**. Those
  133 were random addresses landing on `COUNTER` and `STATUS`, whose values the
  scoreboard cannot predict. A correctly-addressed RAL never touches them by
  accident, so every single read is now checked.
- **`cg_register_offset  8/8`** on a bundle that had been reading 8/8 *for the
  wrong reason* — random addresses hit every offset by chance. It now reads 8/8
  because the RAL walks all eight registers deliberately.

The second one is the uncomfortable part: **a coverage number that was green
while the mechanism under it was broken.** Coverage says stimulus reached a bin.
It does not say the stimulus meant to.

## What it says about the environment

This is [BUG-010](BUG-010.md)'s twin, and the pair is the more interesting object
than either alone. Both are constraints that **compile, elaborate and mean
something other than what they say**:

| | BUG-010 | BUG-013 |
|---|---|---|
| Wrote | `soft (a) -> b dist {…}` | `addr == local::t.addr` |
| Meant | "softly prefer this distribution" | "pin this to what I set" |
| Actually | selected the wrong grammar production | constrained a variable to itself |
| Caught by | a second **front end** | a second **simulator run** |

Neither is catchable by review of the surrounding code — both read correctly.
BUG-010 was ill-typed, so a conformant parser found it in 0.2 seconds. BUG-013 is
perfectly well-typed, so **no parser can find it**; it took actually running the
thing and looking at the numbers.

That is the honest limit of the elaboration gate that has otherwise served this
project well: `make elab` proves the source is legal, not that it is right.

It is also the sharpest possible argument for running the RAL at all. Nothing
else in the environment goes through `reg2bus`, so this code had never executed —
and the first run of it produced 644 errors in a design that is correct.
