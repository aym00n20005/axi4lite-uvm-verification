# BUG-011 — The reference model did not know reset had happened

*Genuine defect, found in the testbench. Not injected.*

| Field | Content |
|---|---|
| **ID** | BUG-011 |
| **Class** | Genuine find — fifth, and the fifth to be in the testbench rather than the design |
| **Located in** | `tb/env/axi_scoreboard.sv` |
| **Detected by** | `axi_reset_seq`, on its first run against Xcelium |
| **Test + seed** | `axi_protocol_test`, seed 1 |
| **Status** | Fixed. The scoreboard now subscribes to the monitor's reset port. |

---

## Expected

Specification §5 gives every register a reset value. `ARESETn` therefore returns
`SCRATCH` to `0x0000_0000` and `CONFIG` to `0x0000_00FF`, and a read afterwards
must see those.

## Actual

Four `UVM_ERROR`s, all of this shape:

```
UVM_ERROR @ 765000: uvm_test_top.env.sb [SB] RDATA mismatch on READ REGION_REG_IMPL
  addr=0x00000014 : got 0x00000000 expected 0xa5a55a5a
UVM_ERROR @ 815000: uvm_test_top.env.sb [SB] RDATA mismatch on READ REGION_REG_IMPL
  addr=0x00000008 : got 0x000000ff expected 0x00000055
```

Read them the right way round. **`got` is the DUT and it is correct.** `expected`
is the model, and it is holding the values the sequence wrote *before* the reset.

The most useful line in the log is the one immediately after each error:

```
UVM_ERROR ... [SB] RDATA mismatch ... got 0x00000000 expected 0xa5a55a5a
UVM_INFO  ... [axi_reset_seq]   PASS  SCRATCH back to 0    0x00000000
```

The sequence's own check **passed on the same read, at the same instant**. The
sequence knew what reset means. The model did not.

## Root cause

`axi_scoreboard` had no reset handling at all. Its register model was
initialised once at construction and only ever updated by observed writes, so
`ARESETn` was invisible to it.

That was correct for every test that existed before this one: nothing had ever
asserted reset mid-simulation, so the model was never wrong. F09 is the first
test to do it, and it is the first thing to look.

## Fix

The monitor already published reset events on a second analysis port — it was
built that way for `cg_reset`. The scoreboard now subscribes to the same port:

```systemverilog
uvm_analysis_imp_rst #(axi_reset_event, axi_scoreboard) rst_export;

function void write_rst(axi_reset_event ev);
    m_ctrl_enable = 1'b0;  m_config     = 8'hFF;
    m_int_enable  = 4'h0;  m_int_status = 4'h0;
    m_scratch     = 32'h0; m_status_error = 1'b0;
    m_counter_zero = 1'b1;
endfunction
```

**The memory arrays are deliberately untouched**, and that is the half of the fix
worth checking in review. Spec §6:

> Reset does **not** clear memory contents. This matches real RAM and is stated
> explicitly so it isn't mistaken for a bug during scoreboard bring-up.

Clearing them here would have been the obvious symmetry, and it would have broken
the one check in `axi_reset_seq` that distinguishes a correct memory from a
cleared one — `memory SURVIVES reset (section 6)`, which passed throughout.

## Regression

`axi_protocol_test` re-run: the four mismatches are gone, `SB` reports the resets
it modelled, and `memory SURVIVES reset` still passes.

## What it says about the environment

The same thing [BUG-008](BUG-008.md) said, from the other direction. That one was
an assertion that failed on correct hardware because its window assumed something
the spec did not bound. This is a **reference model** that failed on correct
hardware because it assumed something the spec explicitly warns about.

Both are false positives, and a false positive is the worse kind of defect: a
checker that cries wolf gets ignored, and is then worthless when it is right.

It is also an argument for the sequence-level checks existing at all. The
scoreboard and the sequence check the same reads by different routes, and the
value of that is entirely in what happens when they disagree — here, the
disagreement pointed straight at which of the two was wrong.
