# BUG-004 — INT_STATUS implemented as a plain RW register

*Injected deliberately, to qualify the testbench. Specification §9.*

| Field | Content |
|---|---|
| **ID** | BUG-004 |
| **Class** | Injected — the last of the six §9 qualification bugs |
| **Located in** | `rtl/axi4lite_reg_slave.sv`, the `INT_STATUS` `always_ff` block |
| **Detected by** | The directed F12 check, the scoreboard, and the formal proof — all measured. **NOT** by the §9-assigned RAL `bit_bash`, which cannot detect it. See below. |
| **Test + seed** | `axi_ral_test` seed 1 on Xcelium — 5 `UVM_ERROR`; also `sanity_tb` and `make formal` |
| **Status** | Detected, reverted. |

---

## Expected

Specification §5:

> **W1C semantics:** bit *n* clears if and only if `WDATA[n] == 1`. Writing 0
> leaves the bit unchanged.
>
> Example — `INT_STATUS` is `4'b1011`, software writes `4'b0011` → result
> `4'b1000`. Bits 0 and 1 clear; bits 2 and 3 are untouched.

## The injection

One word:

```systemverilog
for (int i = 0; i < INT_STATUS_W; i++) begin
    if (int_set[i])                        int_status_q[i] <= 1'b1;
-   else if (w1c_write && wr_data[i])      int_status_q[i] <= 1'b0;
+   else if (w1c_write)                    int_status_q[i] <= wr_data[i];
end
```

The bit now takes the written value instead of being cleared by a written 1.
Writing `4'b0011` to `4'b1011` yields `4'b0011` rather than `4'b1000` — every
bit written as 0 is cleared, and every bit written as 1 is *set*.

It is a plausible defect precisely because the line still looks like it is doing
something deliberate with `wr_data`, and because the register still responds
`OKAY` and still changes when written.

## Detection

**Three independent mechanisms, and each says something different.**

### 1. RAL access-policy test — §9's assigned mechanism. IT DOES NOT WORK.

This was run. `bit_bash` reported **nothing**:

```
[uvm_reg_bit_bash_seq] Verifying bits in register regmodel.INT_STATUS in map "regmodel.axi_map"...
...
[axi_ral_seq]   bit_bash complete
** Report counts by id
[uvm_reg_bit_bash_seq]     8          <- eight INFO lines, zero errors
```

Eight INFO lines, one per register, and not a single `UVM_ERROR`. It was equally
silent on the **correct** DUT, which is the tell: a check that passes on both a
correct design and a broken one is not checking.

**Root cause, from the UVM source.** `uvm_reg_field::configure()`,
[`uvm_reg_field.svh:818`](../../third_party/uvm-1.2/src/reg/uvm_reg_field.svh):

```systemverilog
m_check = volatile ? UVM_NO_CHECK : UVM_CHECK;
```

Declaring a field **volatile sets its compare mode to `UVM_NO_CHECK`**. And
`uvm_reg_bit_bash_seq` builds its don't-care mask straight from that:

```systemverilog
dc = (fields[k].get_compare() == UVM_NO_CHECK);
...
for (int k = 0; k < n_bits; k++) begin
   if (dc_mask[k]) continue;              // <-- the bit is never bashed
   bash_kth_bit(rg, k, mode[k], maps[j], dc_mask);
end
```

Every one of `INT_STATUS`'s fields is declared `volatile: true` in
`scripts/regmap.yaml`, and that declaration is **correct** — hardware sets
`unimpl`, `misalign`, `strobe` and `overflow` without a bus write, which is the
entire purpose of the register. Marking them non-volatile would make
`hw_reset` and every `mirror()` produce false failures the moment the DUT set a
bit on its own.

So the two facts are jointly unavoidable:

- `INT_STATUS` **must** be volatile, or the RAL produces false failures.
- A volatile field is invisible to `bit_bash`, so its access policy is **never
  checked**.

`uvm_reg_hw_reset_seq` has the same blind spot for the same reason — it checks
via `regs[i].mirror(status, UVM_CHECK, ...)`, and `uvm_reg::do_check` skips any
field whose `get_compare()` is `UVM_NO_CHECK`.

**§9 assigned this bug to a mechanism that is structurally incapable of catching
it.** That assignment was written in August, before the RAL existed, from a
reasonable-sounding premise — "the access policy is declared once, so library
code checks the DUT against it" — that turns out to be false for exactly the
class of register where the policy is most interesting.

#### Could it be made to work?

`set_compare(UVM_CHECK)` can be called after `configure()` to re-enable
comparison on a specific field. During `bit_bash` no hardware events occur —
every RAL access is aligned, full-strobe and to an implemented offset — so the
false-failure risk that justifies `volatile` is absent in that window
specifically.

**This is a proposal, not a result. It has not been run**, and it would need the
compare mode restored afterwards or `hw_reset` and `mirror()` become fragile.
Recording it as an untested idea rather than a fix.

### 2. The directed F12 check and the scoreboard — WHAT ACTUALLY CAUGHT IT

Five `UVM_ERROR`s, from two independent mechanisms:

```
[SB] RDATA mismatch on READ addr=0x00000010 : got 0x00000007 expected 0x00000001
[axi_ral_seq]   PASS  hardware set [0]                     0x00000001
[SB] RDATA mismatch on READ addr=0x00000010 : got 0x00000000 expected 0x00000001
[axi_ral_seq]   FAIL  writing 0 does NOT clear it   0x00000000 (expected 0x00000001)
[SB] RDATA mismatch on READ addr=0x00000010 : got 0x00000001 expected 0x00000000
[axi_ral_seq]   FAIL  writing 1 clears it           0x00000001 (expected 0x00000000)
```

Look at the first pair. The scoreboard reports a mismatch **on the same read
where the sequence's own check reports PASS.** The directed check masks to bit 0
and finds the 1 it expected; the scoreboard compares the full word and sees
`0x7` — bits [2:0] all set, residue from `bit_bash`'s writes that the injected
DUT stored instead of clearing.

**The scoreboard was strictly stronger than the directed check at that instant**,
and it was stronger precisely because it is not looking for anything in
particular. A check written to ask one question gets one question's worth of
answer.

### 3. A directed check — `sanity_tb`, local — MEASURED

```
  FAIL   W1C cleared only bits 0 and 2                0x5   (expected 0x2)
```

1 of 31 checks. It catches it because someone thought to write the spec's own
worked example down as a test.

### 4. Bounded model check — `make formal`, local — MEASURED

```
Assert failed in axi4lite_reg_slave: f_w1c_no_spurious_set
```

`f_w1c_no_spurious_set` says a bit that was clear, with no hardware event, stays
clear. A plain-RW register violates it the moment a 1 is written to a clear bit.

That property exists *because* of a worry recorded when it was written: without
it, a register that sets bits spontaneously satisfies every other W1C property in
the file. It was added defensively and it is the one that fired.

## Root cause

Not a misunderstanding of W1C — a misunderstanding of which operand carries it.
`wr_data[i]` is the *condition* for a clear, not the *value* to store. Both
readings type-check, both compile, both produce a register that changes when
written, and only one of them is a status register.

## Fix

Reverted.

## Regression

`sanity_tb` 31/31, `sanity_mem_tb` 27/27, `sanity_sys_tb` 36/36, `make formal`
PASSED at depth 25 and 40, no assertion fired.

## What it confirms about the environment

The bug was caught, decisively, by three independent mechanisms. It was **not**
caught by the one the specification named, and the reason is a documented
property of UVM that no amount of reading my own code would have surfaced.

That is the whole return on running the injection instead of reasoning about it.
The previous revision of this report claimed `bit_bash` caught this, with an
invented log excerpt. Correcting that to "predicted, not yet measured" was right.
**Running it showed the prediction was not merely unproven but false**, for a
reason worth more than the confirmation would have been:

> A field that is volatile — the exact case where hardware behaviour is most
> worth checking — is the case UVM's register sequences silently stop checking.

The generated-register-model argument still holds for the seven non-volatile
registers, where `bit_bash` and `hw_reset` do real work against a model nobody
transcribed by hand. It does not hold for `INT_STATUS`, and this project can now
say exactly where the line is instead of assuming there isn't one.

The §9 table is corrected accordingly: **five of six** injections were caught by
their assigned mechanism, and BUG-004 was caught by three others while the
assigned one proved structurally blind.
