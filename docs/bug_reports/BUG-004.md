# BUG-004 — INT_STATUS implemented as a plain RW register

*Injected deliberately, to qualify the testbench. Specification §9.*

| Field | Content |
|---|---|
| **ID** | BUG-004 |
| **Class** | Injected — the last of the six §9 qualification bugs |
| **Located in** | `rtl/axi4lite_reg_slave.sv`, the `INT_STATUS` `always_ff` block |
| **Detected by** | A directed check and a bounded model check, both measured. The §9-assigned RAL detection is **predicted, not yet measured** — see below. |
| **Test + seed** | `sanity_tb` (Verilator, 1 of 31 checks) and `make formal` (`f_w1c_no_spurious_set`) |
| **Status** | Detected, reverted. |

---

## Expected

Specification §5:

> **W1C semantics:** bit *n* clears if and only if `WDATA[n] == 1`. Writing 0
> leaves the bit unchanged.
>
> Example — `INT_STATUS` is `4'b1011`, software writes `4'b0011` → result
> `4'b1000`. Bits 0 and 1 clear; bits 2 and 3 are untouched.

## The injection

One word:

```systemverilog
for (int i = 0; i < INT_STATUS_W; i++) begin
    if (int_set[i])                        int_status_q[i] <= 1'b1;
-   else if (w1c_write && wr_data[i])      int_status_q[i] <= 1'b0;
+   else if (w1c_write)                    int_status_q[i] <= wr_data[i];
end
```

The bit now takes the written value instead of being cleared by a written 1.
Writing `4'b0011` to `4'b1011` yields `4'b0011` rather than `4'b1000` — every
bit written as 0 is cleared, and every bit written as 1 is *set*.

It is a plausible defect precisely because the line still looks like it is doing
something deliberate with `wr_data`, and because the register still responds
`OKAY` and still changes when written.

## Detection

**Three independent mechanisms, and each says something different.**

### 1. RAL access-policy test — §9's assigned mechanism, and NOT YET MEASURED

This is the detection that would matter most, because **nobody would have written
a test for it**: the access policy is stated once in `scripts/regmap.yaml`, and
`uvm_reg_bit_bash_seq` — library code that has never read this project's
specification — checks the DUT against it. A hand-written access-policy test and
a hand-written register bank are two transcriptions of one table by one person,
and they agree with each other's mistakes.

**But it has not been run, and this report previously said it had.** That was
wrong, and the correction is worth more than the claim was.

The RAL's first real execution found [BUG-013](BUG-013.md) — a tautological
constraint in `axi_reg_adapter::reg2bus` that sent every register access to a
*random address with random data*. So the run that was supposed to qualify the
RAL instead disqualified it, at 644 `UVM_ERROR`s against a correct design. Until
a clean `axi_ral_test` passes, the mirror has never been compared against this
DUT at all, and no claim about `bit_bash` catching anything is measured.

The mechanism is sound and the prediction is specific — `bit_bash` predicts
`cur_val & ~wr_val` for a `W1C` field, a plain-RW DUT returns `wr_val`, and they
disagree on the first bit — but a prediction is what it is.

### 2. A directed check — `sanity_tb`, local — MEASURED

```
  FAIL   W1C cleared only bits 0 and 2                0x5   (expected 0x2)
```

1 of 31 checks. It catches it because someone thought to write the spec's own
worked example down as a test.

### 3. Bounded model check — `make formal`, local — MEASURED

```
Assert failed in axi4lite_reg_slave: f_w1c_no_spurious_set
```

`f_w1c_no_spurious_set` says a bit that was clear, with no hardware event, stays
clear. A plain-RW register violates it the moment a 1 is written to a clear bit.

That property exists *because* of a worry recorded when it was written: without
it, a register that sets bits spontaneously satisfies every other W1C property in
the file. It was added defensively and it is the one that fired.

## Root cause

Not a misunderstanding of W1C — a misunderstanding of which operand carries it.
`wr_data[i]` is the *condition* for a clear, not the *value* to store. Both
readings type-check, both compile, both produce a register that changes when
written, and only one of them is a status register.

## Fix

Reverted.

## Regression

`sanity_tb` 31/31, `sanity_mem_tb` 27/27, `sanity_sys_tb` 36/36, `make formal`
PASSED at depth 25 and 40, no assertion fired.

## What it confirms about the environment

Two mechanisms caught it, both measured, and each says something different: a
person wrote the spec's worked example down as a directed check, and a property
added defensively to the formal file — `f_w1c_no_spurious_set`, there because
without it a register that sets bits on its own satisfies every other W1C
property — fired.

**What it does not yet confirm is the RAL**, and that is the honest state of it.
The argument for generating the register model from one YAML is exactly that the
model checking the DUT was never transcribed by the same hand that wrote the DUT
— but an argument is not a measurement, and this one is outstanding until a clean
`axi_ral_test` runs and is then re-run against this injection.

The correction itself is the point. A mechanism that has never caught a bug is
unproven; a report that *says* a mechanism caught a bug when the mechanism never
ran is worse, because it looks like evidence. This project's own standard —
"nothing goes here until it is measured" — applies to its bug reports too.
