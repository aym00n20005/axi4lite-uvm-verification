# BUG-012 — `STATUS.error` predicted for a read the model cannot place

*Genuine defect, found in the testbench. Not injected.*

| Field | Content |
|---|---|
| **ID** | BUG-012 |
| **Class** | Genuine find — sixth, and the sixth to be in the testbench |
| **Located in** | `tb/env/axi_scoreboard.sv`, `check_read`'s `SB_STATUS` case |
| **Detected by** | `axi_status_seq`'s F24 sweep, on its first run against Xcelium |
| **Test + seed** | `axi_register_test`, seed 1 |
| **Status** | Fixed. `STATUS` is masked for a read that overlapped a write. |

---

## Expected

Specification §5: `STATUS.error` is 1 when the most recently **completed**
register transaction returned `SLVERR`. The scoreboard models it and checks it,
masking only bit 0 (`busy`), which is cycle-level.

## Actual

One `UVM_ERROR`, at the first iteration of F24's sweep:

```
UVM_ERROR @ 10185000: uvm_test_top.env.sb [SB] RDATA mismatch on READ REGION_REG_IMPL
  addr=0x00000004 : got 0x00000002 expected 0x00000000
```

Again, `got` is the DUT and it is right. Every one of `axi_status_seq`'s nine
checks passed, including the sweep's own.

## Root cause

`STATUS.busy` is only observable if a read overlaps an in-flight write —
`verification_plan.md` §9 asked exactly this question, and `axi_status_seq`
answers it by issuing both non-blocking so they are on the bus together. Spec §1
permits precisely that: one read and one write in flight at once.

But the overlap that makes `busy` observable makes `error` **un**observable to a
transaction-level model, and the two facts are the same fact:

- The DUT updates `status_error` at the write's internal **commit**, one cycle
  before its `B` response.
- The scoreboard sees transactions in **completion** order and has no way to
  place a read's sampling instant relative to another transaction's commit.
- Spec §5 even names the tie-break — *"if a write and a read complete on the same
  cycle, the **write** determines the resulting value"* — which is a statement
  about a clock edge, and this model does not have clock edges.

So the model cleared `m_status_error` when it processed the write, and the read
had already sampled the DUT while the earlier `SLVERR` was still reflected.

## Fix

The monitor records, at the AR accept, whether a write was in flight — from
**its own accept queues**, not by asking the driver:

```systemverilog
beat.obs_overlapped_write = (aw_accepted.num() != 0) || (w_accepted.num() != 0);
```

and the scoreboard masks the whole of `STATUS` for such a read:

```systemverilog
mask = t.obs_overlapped_write ? 32'h0000_0000 : 32'hFFFF_FFFE;
```

Masked, not fudged, and **recorded as skipped** — the scoreboard's `check_phase`
already reports read data it declined to predict, so "not checked" can never be
mistaken for "checked and passed".

## Regression

`axi_register_test` re-run: 0 `UVM_ERROR`, 60/60 sequence checks, and `busy
observed as 1 at least once` still passes — the mask removes a false failure
without removing the observation the sweep exists for.

## What it says about the environment

This is the third field the model declines to predict, and the list is now
coherent rather than incidental:

| Field | Unpredictable because |
|---|---|
| `STATUS.busy` | cycle-level by definition |
| `COUNTER` | free-running; checkable only in the cleared-and-frozen state |
| `INT_STATUS[3]` | follows `COUNTER` |
| **`STATUS.error`, on an overlapped read** | the DUT updates it at a commit the model cannot order against a concurrent read |

Every one of those is masked in `tb/ral/axi_reg_block.sv` too, at the same
places, so two independently written models make the same claim about what is
knowable from transactions alone.

The general lesson is worth more than the fix: **the stimulus that makes one
field observable made another one unpredictable.** F24 could not have been
written without creating this, and the answer is not to weaken the test — it is
to say precisely which claim the model can no longer make, and stop making it.
